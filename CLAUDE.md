# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Iron Arena is a 2D top-down **battle-royale** tank IO game (Diep.io-inspired). Flow: Main Menu → Waiting Room (30s countdown, customize) → Match → Death/Victory screen → (Play Again / Main Menu). A match has a **fixed roster** (player + bots up to `match.matchSize`, no respawns, deaths permanent, last tank alive wins). In-match upgrades are **collected as world pickups + loot crates** (rarity zones), shown in a bottom-right HUD — there is no buy-menu. A **toxic fog** shrinks in **timed stages** (hold, then contract — so players can rotate) and **stops at a final battle zone** (`fog.finalRadius`); it does stronger DoT and flashes a red HUD warning while you're outside it, and **intensifies in the endgame** (faster cycle + loot lost outside it as the roster thins). **Arena Guardians** **patrol** the high-loot center (orbit, stop to fire, never chase); procedural **walls** (impassable, block bullets) break up the map. A screen-space **minimap** shows the player, obstacles, the current safe zone + a **dashed next zone** — and reveals enemy tanks **only with the Radar special** (guardians/crates/upgrades are never shown). AI bots are the *same species* as the player (identical `Tank` driven by a `BotBrain`). **Iron Path** is the meta-progression: XP earned per match → level 1–60, unlocking a new weapon every 6 levels; the **Arsenal** equips unlocked weapons (each with a distinct turret). The **Cosmetics** locker (live showcase + sliding tabs) covers colors, body **wraps**, movement **trails**, **kill FX**, and **titles** — and now shows only **unlocked** items (plus a "??? Unlock more" card). Unlocks are *derived* from progression (Iron Path level + completed achievements). **Achievements** grant **money** ($) and titles, fire a top-center completion **toast**, and flag a menu badge; a **Shop** screen is scaffolded (Coming Soon). Loot **crates are shot open** and **scatter** their items outward as collectible pickups (nothing auto-granted); already-owned upgrade pickups are **ghosted** and skipped; a special pickup while holding 2 shows a **[F] to swap** prompt that **physically ejects** the replaced (oldest) special back into the world in front of you. The **main menu is alive** (bots wander + shoot harmlessly, slow camera drift) behind a translucent panel. Nametags are team-colored (player white, enemies light red). The world is a clean Diep-style **light** theme; tanks carry momentum (accel/glide) and the turret recoils on fire. UI is a flat style (no glow/blur/gradients) using Exo 2 (titles) + Ubuntu (body). Multiplayer is being built in phases: **Phase 1 foundation is done** — an authoritative Node.js WebSocket server (`server/index.js`, `npm run server`) + a client `MULTIPLAYER` mode (`src/net/`) give real browser clients a shared, server-authoritative arena (movement, aim, Standard-turret shooting, projectiles, damage, death, disconnect). The single-player BR (bots as placeholders) is unchanged and runs in parallel; the full networked 30-player BR is a later phase.

The **weapon system follows the authoritative Core Weapon Concepts PDF** — all 11 Arsenal weapons in the PDF's exact order with distinct turret silhouettes; every stat lives in `config.js` (`GAME.weapons`, absolute values, balanced around 100 HP). Order: Standard, Dual Barrel (two full-damage barrels), Machine Gun (trapezoid, high spread), Flank (front+rear barrels), Sniper (long barrel, +FOV camera zoom, armor-pierce), Triple Barrel (**angled fan**), Rocketeer (arrowhead rocket that **trails small bullets out its back** + **SHIFT-detonates** into pellet rings), Penta Shot (5-barrel fan, sizes **decreasing** middle→outer, staggered), **Burst Rifle** (replaces Railgun — one barrel, **3-round burst + reload**, muzzle-notch), Cannoneer (huge slow shell), Laser Rifle (finite-range beam with a **heat/overheat** system — barrel glows red, overheats after `heatTime`, locks out for `coolTime`; re-purposes Bullet-Speed/Reload upgrades as Laser Damage/Lethality). A developer **TEST** button (main menu, below Achievements) instantly unlocks everything (weapons/cosmetics/titles), completes the Iron Path + achievements, and grants money. Iron Path **currency rewards** credit the profile on level-up.

Controls: WASD move · mouse aim · left-click shoot · Space dash (with Flash special) · SHIFT detonate rocket (Rocketeer) · F toggle FPS.

## Tech Stack

- **Rendering:** PixiJS v8 (async `Application.init()`, WebGL/WebGPU)
- **Build/dev:** Vite 6, ES modules
- **Server:** Node.js + WebSocket (`ws`) — authoritative multiplayer server in `server/index.js` (`npm run server`, port 8080). Imports the game's `src/config.js` so client + server share the real Standard stats.
- **Accounts / persistence:** `better-sqlite3` (SQLite, single local file, ACID, $0) behind a swappable `AccountStore` interface in `server/accounts/` — persistent, server-authoritative player accounts (identity, XP/level, currency, unlocks, loadout, stats). Degrades gracefully to a JSON-file store, then in-memory, so the server never crashes over storage. Env: `IRON_DB` (`sqlite`|`json`|`memory`), `IRON_DATA_DIR` (data location; default `server/data/`, gitignored). Offline PLAY needs no account/server.

## Code Structure

- `src/main.js` — entry point; imports the overlay CSS, creates the `Engine` + `Input`, and hands off to `GameFlow`. No gameplay assembly here.
- `src/sim/` — the **headless authoritative world model** (Phase 14.2 Step 1): renderer-free game simulation with **zero Pixi/DOM imports**, so the exact same logic runs on the server today and (later) the client. `constants.js` resolves the authoritative `SIM` physics from `config.js` (Standard + player base); `physics.js` holds the pure movement/projectile/collision helpers (`integrateMovement`/`stepBullet`/`circleOverlap`) — the **single shared implementation**: the client `Tank.update`/`Bullet.update` and `Game.#overlap` DELEGATE to these (Step 2). **Step 3** added `FogModel.js` (authoritative toxic-fog/zone: radius, staged shrink cycle, `isOutside` — the client `Fog` is now a thin Pixi wrapper that only draws from it), `UpgradeState.js` (moved from `game/`; re-exported there for compat), and `upgradeStats.js` (`deriveUpgradeStats` + `resolveEntityStats(weapon, normals)` — the pure upgrade→effective-stats resolver the client's `#applyStats`/`#applyBotStats` now call). `WorldModel` gained `resolveStats(id)` (upgrade-aware) + an opt-in `FogModel` (off by default, so the server stays identical). **Step 6b** added `weapons.js` — a pure, DATA-DRIVEN weapon-firing interpreter (`resolveShots`/`shotToProjectile`/`rocketProjectile`/`fireModeOf`) that reads a `GAME.weapons` entry + resolved stats and produces projectiles; `WorldModel.#weaponUpdate` dispatches on `fireMode` so ALL 11 weapons fire authoritatively (multi-barrel/spread/staggered salvos, 3-round burst, Rocketeer rocket + rear-trails + SHIFT detonation, Laser beam raycast + heat/overheat), with per-bullet damage/radius/armor-pierce/pierce/shape. A new weapon defined via the config schema is automatically multiplayer-compatible — no networking or per-weapon MP code (proven by adding a runtime "Test Heptashot"). **Step 4** made the model AI-drivable: bot entities carry the fields the shared `BotBrain`/`ai/*` read (`rotation`/`radius`/`bounds`/`_hitTimer`/`dead`/`_bulletSpeed`), and `WorldModel.aiView()` returns a `game`-shaped perception adapter — so the EXISTING bot AI drives world-model entities via `think() → setInput() → step()` with zero Pixi (proven by `test-bot-ai.mjs`: an 8-bot BR resolving to one winner in pure Node). The AI only READS `aiView()` and returns intent; the model owns every outcome (movement/firing/damage/death). The client single-player game is untouched (still runs bots through the client `Tank`); `WorldModel.js` is the authoritative container — plain entity records (`{id,type,team,x,y,vx,vy,rot,hp,maxHp,alive,weapon,input,fireCd,+per-entity stat fields}` — deliberately separate from any render view), `bullets[]`, and a `step(dt)` doing movement→firing→projectiles→collision→damage→death→`onKill`, plus `setInput()` (unit-disc-clamped, anti-teleport), `snapshot()`, and `respawn()`. Structured to receive fog/zone, guardians, loot/crates, upgrade-resolved stats, and bot-AI-driven input in later steps (the AI modules are already pure). `test-headless.mjs` proves it runs in Node with no browser.
- `server/index.js` — the **authoritative multiplayer server** (Node + `ws`, `npm run server`). A thin networking shell around the shared `src/sim/WorldModel`: clients send INTENT only (`join`/`input`/`respawn`/`ping`); the server steps the world model at a fixed 30 Hz and broadcasts its `snapshot()` as `state` + `welcome`/`kill`/`leave`. Anti-teleport by construction (clients never send positions). **Step 5** added **server-side bots** (env `MP_BOTS`, default 8): real `BotBrain`s (fresh genome, Node-safe) attached to world-model bot entities and driven each tick via `world.aiView() → setInput → step` — so humans + bots share ONE authoritative match and every client sees the SAME bot state; bots refill on human join, and the sim pauses when no human is connected. `server/test-clients.mjs` (human-only, run with `MP_BOTS=0`) + `server/test-step5.mjs` (humans + bots) are the headless multi-client harnesses.
- `src/net/` — the client multiplayer layer. `NetClient.js` is a thin WebSocket wrapper (connect/join/`sendInput`/ping, graceful error/disconnect handling via `onStatus`) that surfaces server messages via callbacks and never decides outcomes. `MultiplayerMode.js` is a self-contained mode that reuses the existing `Engine`/`Tank`/`Input`: the local player is a real input-driven `Tank` with **light client prediction + soft server correction**; remote players are `Tank`s interpolated from snapshots; bullets are reconciled to the server's list and extrapolated between snapshots; a dev status HUD (id/players/ping) + a death/respawn overlay round it out. It runs while the single-player `Game` is **paused** (GameFlow `#startMultiplayer`/`#exitMultiplayer` hand the engine over via the `MULTIPLAYER` menu button).
- `src/game/GameFlow.js` — the match-flow **state machine** (menu → waiting → playing → dead/won). Owns the `Profile`, the `Game`, and the DOM screen overlays (incl. `WinnerScreen`), and wires button clicks / countdown / death / victory to Game lifecycle calls. No networking.
- `server/accounts/` — the **persistent, server-authoritative account layer** (Phase 14.2 Step 7). `ids.js` maps GAME array items ↔ STABLE ids (name slugs) so accounts store order-independent ids while the client keeps its index-based UI (the wire stays indices; this is the translation seam). `auth.js` — token-based guest identity (random secret token per account; server stores only a salted **scrypt hash**, never plaintext; `node:crypto` only). `account.js` — the pure account model + all authoritative progression logic (defaults incl. always-unlocked Blue/Standard, `grantXp`→level-up→Iron Path reward+currency grant guarded by `claimedRewards`, `applyLoadoutIndices` validation with fallback, `recordMatch` stats, `toProfileWire` → the client's index-based profile). Player level == Iron Path level (no parallel curve). `store.js` — the `AccountStore` (SQLite via `better-sqlite3`; structured columns for identity/xp/currency/loadout + JSON columns for the collection-shaped unlock sets/claimed rewards/stats, so new stats/categories need no migration) with JSON-file and in-memory fallbacks. `service.js` — `AccountService`, the only path that mutates persistent progression (login/auth, `awardXp`, `recordMatch`, `setLoadout`, `profile`). Tests: `test-accounts.mjs` (creation/persistence/unlocks/currency/loadout/security/isolation, both backends) + `server/test-accounts-net.mjs` (over-the-wire auth, authoritative match XP, persistence across a server RESTART, tamper rejection, isolation).
- `src/net/AccountClient.js` — client credential holder: persists `{accountId, token}` in `localStorage`, builds the `auth` message. The server owns all progression; this is a tiny, replaceable identity shim (a real login screen would populate the same pair).
- `src/game/Profile.js` — persisted player identity (username, weapon index, `ironPathXp`, `money`, `achievements`, `devUnlockAll`, `accountId`, and cosmetic indices: `cosmetic` color, `wrap`, `trail`, `killFx`, `title`) via `localStorage`. `displayName` falls back to "Unnamed Tank". `applyServerProfile(wire)` adopts the server's authoritative account profile online (XP/currency/loadout mirror; unlocks stay DERIVED from XP since the server grants match that derivation); `online` flags an active account. Offline this is a standalone local cache (unchanged). `ironPathLevel` getter derives the level from XP; `addIronPathXp(n)` awards match XP, **grants any Iron Path currency rewards for the levels just reached**, and returns levels gained. `devUnlockAll` is the developer-TEST flag. This is the single local **player profile** (no accounts/backend).
- `src/game/IronPath.js` — pure Iron Path progression helpers over `GAME.ironPath`: `levelForXp()`, `levelProgress()`, `unlockLevel(weaponIndex)`, `isWeaponUnlocked(level, i)`, `earnedXp({kills,survival,won})`. Single source of truth for the curve + weapon-unlock schedule. (`GAME.ironPath.rewards` defines the **complete authoritative L1–60 reward schedule** — `title`/`money`/`wrap`/`trail`/`killfx`/`color`/`weapon`, plus the L60 **`bundle`** whose `items[]` hold 7 rewards; weapons also derive from `unlockEvery`, and the two agree at 6·i.)
- `src/game/achievements.js` — achievement definitions (id/name/desc/goal/reward). `src/game/Progression.js` — achievement progress + reward granting (money + title unlock), unseen-badge count, mark-seen. `src/game/unlocks.js` — `unlockedIndices(profile, category)` derives unlocked cosmetics (colors/wraps/trails/killFx/titles) from Iron Path reward level (unpacking the L60 bundle's items) + completed achievement titles — never stored. **Index 0 of every category is the always-available default** (Blue color / None wrap+trail / No Kill FX / No Title).
- `src/engine/` — gameplay-agnostic core. `Engine` owns the Pixi `Application`, the world `Container`, the camera, and the frame loop. Each tick it (1) updates+syncs all entities, (2) runs registered **systems** (`addSystem`), (3) reaps entities flagged `dead` and destroys their views, (4) applies the camera. `Camera` smoothly lerps toward its `target` (`followSpeed`), clamps the view to `bounds`, supports `shake()`, and exposes `screenToWorld()` for cursor aim. `Input` is a passive keyboard/mouse state holder (`isDown`, `moveAxis`, `mouse`, `isFiring`); `wasPressed(code)` is an edge-trigger for toggles/menus (consumed once per press).
- `src/entities/` — world objects: `Tank` (used for player, bots, AND guardians — identical structure; player has `input`+`camera`, others have an `ai` brain; carries `team`, `level`, `armor`, `turret`, `wrap`; `setWeapon(w)` rebuilds the turret barrels, `setColor`/`setWrap` restyle the body; momentum via eased velocity + a turret `recoil` on fire), `Bullet` (straight-line, `team` so it only hits the other side; `shape` circle/hex/star, `armorMul` for pierce/vulnerability, `pierce` count, `knockback`), `UpgradePickup` (rarity-ringed circle / special hex, drawn with the shared upgrade icon), `Crate` (chunky brown reinforced loot container holding 3 upgrade `items`; **shot open** — takes bullet damage, then scatters its items), `UpgradePickup` also supports `vx`/`vy` + a `pickupDelay` (scattered crate loot / ejected specials fling out then settle), `Wall` (static impassable rectangle; blocks movement + bullets), `Drone` (sentry/loot companion orbiting the player), `Particle` + `DamageNumber` (cosmetic). Each owns its world transform + a Pixi view and exposes `syncView()` and optionally `update(dt)`; self-flag `this.dead = true` to be removed.
- `src/game/Game.js` — the gameplay coordinator (NOT in the engine). Runs the **battle-royale** match: fixed roster at start (no respawns), team-based collisions (player/bot/guardian), world-pickup + loot-crate upgrades, specials, toxic fog, guardians, minimap, endgame, win/lose. **Phase lifecycle** (`menu`/`waiting`/`playing`/`dead`/`won`): `showMenuBackground()`, `enterWaiting(profile)`, `startMatch()` (swaps scenery, expands bounds, drops player into the outer ring, spawns roster + guardians + pickups + crates + fog). Two gates: `combatEnabled` (shooting — ON in the waiting room AND the menu, where bots shoot harmlessly behind the UI) and `damageEnabled` (hits/kills/upgrades/fog/XP — match only); the menu also slow-drifts the camera (`#driftMenuCamera`). Shooting a crate `#breakCrate`→`#scatterItem` flings its loot out as pickups (no auto-grant); `#dropSpecial` ejects a swapped-out special; player shots emit a `#muzzleFlash`; fog DoT flashes a red HUD warning (`Hud` `fogWarn`, gated on `state.fogWarning`). Endgame: `#fogIntensity()` accelerates the fog cycle as the roster thins (`GAME.endgame`), and `#consumeLootInFog()` removes loot left outside the safe zone. `#awardXp()` grants Iron Path XP on match end. **Weapon firing** dispatches on `weapon.fireMode`: `#firePlayer`→`#spawnShot` fires each configured barrel from its muzzle (staggered via a `#processSalvo` timer for Penta AND the 3-round **Burst**), `#fireRocket`/`#rocketTrails`/`#detonateRockets`/`#detonate` handle the Rocketeer (arrowhead rocket + rear-fired trail bullets + SHIFT detonation), and `#fireLaser` casts a proper ray (`#raycast`/`#rayCircle`/`#rayAabb`) that stops at the FIRST blocker — enemy tanks, crates (chipped + broken → scatter), or walls — within the configurable `laser.range`, while tracking **heat/overheat/interrupt** cooldowns and tinting the barrel red (`Tank.setBarrelHeat`); `#bulletHits` applies `armorMul`/`pierce`/`knockback`. Sniper sets `camera.zoom` from `weapon.fovMul`. `#applyStats()` resolves every concrete number from the weapon's config + collected-upgrade multipliers (`deriveUpgradeStats`), including the Laser's re-mapped upgrades. Plugs in via `engine.addSystem`.
- `src/game/upgrades.js` — pure data + helpers for the upgrade system: `RARITIES`/`RARITY_COLOR`/`RARITY_MUL`, `NORMAL_TYPES` (5 stat upgrades), `SPECIALS` (5 abilities), `ZONES` (concentric rarity bands + pickup/special counts), `pickRarity()`, `deriveUpgradeStats()`.
- `src/game/UpgradeState.js` — the player's collected upgrades for a match: `normals` (type→rarity, higher replaces lower, no stacking) + `specials` (max 2; a 3rd drops the oldest).
- `src/game/Fog.js` — toxic fog: a safe radius that shrinks in **timed stages** (hold `holdTime`, contract over `shrinkTime`, repeat) and **stops at `finalRadius`**. Exposes `radius` (current) + `nextRadius` (next shrink target, null once final — minimap draws it dashed), `isOutside(x,y)` for DoT, and a glowing edge ring. Endgame `mul` accelerates the cycle.
- `src/game/BotBrain.js` + `src/game/ai/` — **modular, evolution-ready** bot AI (Bot AI Phase 1). `BotBrain` is the ORCHESTRATOR: on a **throttled** plan tick (`GAME.ai.planInterval`, never every frame) it calls the separate systems — `ai/context.js` `perceive()` (cached snapshot: nearby enemies/loot/guardians/fog, player-available info only), `ai/targeting.js` `chooseTarget()` (scored: distance, enemy HP, fog risk), `ai/objectives.js` `chooseObjective()` (the single active `OBJ.*`: EXPLORE/FIND_CRATE/COLLECT_UPGRADE/ATTACK_ENEMY/CHASE_ENEMY/RETREAT/ROTATE_TO_SAFE_ZONE/FIGHT_GUARDIAN/ESCAPE_DANGER) — then EXECUTES it every frame into `{move, aim}` + a `wantsFire` flag (Game only fires when true; bots don't shoot constantly). Each bot's identity is an `ai/BotProfile.js` **genome**: continuous `skill` 0..1 (tiers/distribution configurable in `GAME.ai`) + `personality` (hunter/scavenger/survivor/guardianHunter/explorer) + evolvable `params` (aggression, riskTolerance, lootPriority, retreatThreshold, aimAccuracy, reactionTime, preferredRange, fogAwareness, wanderiness, targetPreference) — designed so a future offline evolutionary trainer can mutate these numbers without touching AI code (the trainer itself is NOT built). Skill shapes execution only (aim/reaction/prediction/dodge), never raw stats — and only slightly widens perception (beginners still detect enemies from a reasonable distance; nobody is omniscient — `ai/context.js` only reports entities within a skill-scaled `awareness` radius, plus perceived **incoming projectiles** for dodging). Decisions are **tactical, not reflexive**: `ai/objectives.js` weighs a `fightScore` (HP edge, target weakness, being outnumbered, disposition) to choose attack / chase / **WAIT (third-party a busy fight)** / retreat / ignore; the executor positions by **weapon style** (`kite`/`push`/`circle`/`poke` from `ai/BotProfile.js`), **dodges** perceived shots, and does **smart diagonal retreats** (juking + firing back when capable). Aim and dodging are deliberately **imperfect** (micro-balanced so bots feel like very good humans, not aim-bots): a skill-scaled aim-error floor + slightly under-estimated leading, and a dodge (`#dodgeVector`) with a **reaction delay**, a **commit probability** (sometimes misjudges), escape-direction error, and reduced success against **overlapping bullets** — so well-aimed human shots can land. Firing is strictly target-gated (enemy/crate) plus a **rare "bored" shot** while exploring. Bots react dynamically (damage-triggered re-plan; no loot tunnel-vision while `underFire`), score the player like any tank (no "human = always attack"), and **collect upgrades through the authoritative system** (`#botPickups` + per-bot `UpgradeState`; `botCanUse` skips specials/owned so they never get stuck). **All bots wield the Standard turret on the PLAYER's exact base stats** — `Game#applyBotStats` resolves every combat number from `GAME.weapons[0]` (Standard) + `GAME.player` base + `deriveUpgradeStats`, with NO parallel `GAME.bot` combat values (a base bot == a base player). Looting is **value-based, build-aware, and risk-aware** (`ai/loot.js`): `lootValue()` scores an upgrade by marginal stat gain × under-invested category × personality weight; `pickBestLoot()` picks the highest value discounted by distance + nearby-enemy risk (not the nearest); `ai/objectives.js` then pursues only worthwhile loot and abandons it under threat (unless high-value). Firing/leading/preferred range derive from each bot's ACTUAL bullet reach, so upgrades change how a bot plays. The genome adds evolvable `patience`/`opportunism`/`chaseTendency`/`dodgeTendency`/`objectivePersistence`. An **offline evolutionary trainer** lives in `src/game/ai/trainer/` — `sim.js` runs headless Pixi-free BR matches reusing the real `BotBrain`, `evolve.js` scores policies by good BR behaviour (placement + survival dominate; kills/damage help but don't dominate, so it won't breed suicide-rushers), then selects/crosses/mutates **within skill tiers** (preserving a believable beginner→elite spread + a fixed beginner baseline) and saves labelled policies to `localStorage`; the live game loads them per-tier via `pickSavedPolicy()`. It's a dev tool (`window.__ironTrain(gens)` to train, `window.__botDebug(i)` to explain a decision, `window.__botStats(i)` to print a bot's base-vs-final Standard stats + collected upgrades — see `ai/trainer/dev.js`), never run during live play. Each bot has its OWN team so **bots fight each other** (BR matches thin the roster via combat, not just fog); unique per-lobby names from `ai/names.js` (no more "BOT"); `bot.level` derives from the skill tier. `src/game/GuardianBrain.js` — guardian AI: **patrols** an orbit around center (`patrolRadius`/`patrolTurn`), **stops to fire** at the nearest player/bot in range (`hasTarget` gates firing), steers back past `homeRadius`; never chases.
- `src/utils/angle.js` — shared `approachAngle()` (shortest-path angular easing).
- `src/render/` — pure rendering helpers: `shapes.js` (diep-style fill + auto-darkened bold outline), `turret.js` (`turretBarrels(turret, R)` — the **data-driven VISUAL authority** for weapons, separate from gameplay stats: barrel geometry per weapon as `{start, length, w0, w1, perp, angle}` quads where `w0`≠`w1` makes a **trapezoid** and `start`>0 **detaches** a quad from the body (Burst muzzle, Rocketeer collar); proportions authored to match the Core Weapon Concepts PDF. Both renderers draw each quad with a **single gray fill + one darker outline** (`COLORS.tankBarrel` + `darken()`; the pre-redesign border — the earlier two-tone dark-shell/inset-core look was reverted per request, geometry untouched): a rounded rect for straight barrels, a sharp trapezoid when `w0`≠`w1`. Used by BOTH the in-world `Tank` (`#drawBarrel`) and the SVG previews (`svgBarrel`) so they always match — one silhouette per weapon), `upgradeIcons.js` (`drawUpgradeIcon(g, key, color, s)` — flat bold glyph per upgrade, shared by the HUD slots AND the world pickups), `wraps.js` (`drawWrap()` — body wrap patterns, clipped to the tank circle), `Grid.js`, `Arena.js` (floor + border), `HealthBar.js` (eased fill, floats above an entity on its non-rotating view).
- `src/ui/` — two kinds of UI:
  - **In-world Pixi UI** on `app.stage`: `Hud.js` (score / "Alive" BR count / FPS + bottom HP bar + `setPrompt()` + a pulsing red **fog-warning vignette**; dark text for the light world), `UpgradeHud.js` (bottom-LEFT: 5 normal rarity-ringed circle+icon slots, 2 special hex slots, **custom animated hover tooltip**; `setLaserMode()` relabels the Bullet-Speed/Reload slots as **Laser Damage / Laser Lethality** while the Laser Rifle is equipped), and `Minimap.js` (top-right: player dot + wall rects + current safe ring + **dashed next-zone ring**, plus a **fog countdown chip below the box** ("Fog shrinks in Xs" / "FOG MOVING" / "FINAL ZONE"); enemy tanks shown **only with the Radar special**; `update(state)` each playing frame). Note `Minimap` intentionally never plots guardians/crates/upgrades. All `layout()` on resize.
  - **Screen-flow DOM overlays** over the canvas: `MainMenu.js` (entry buttons + money readout + Achievements side-button with unseen badge), `WaitingRoom.js` (countdown banner), `DeathScreen.js`, `WinnerScreen.js` (both show Iron Path XP earned), `CosmeticsPanel.js` (redesigned locker: live tank **showcase** above horizontally-**sliding tabs** — Colors / Wraps / Trails / Kill FX / Titles; shows only unlocked + a placeholder), `LockerPanels.js` (`ArsenalPanel` — weapon **card grid** with lock overlays, `IronPathPanel` — horizontal 1–60 track previewing each level's concrete reward of ANY type (weapon/title/color/wrap/trail/killfx/money/bundle) via shared `rewardMeta()`/`rewardArt()`, with hover tooltips that carry a custom-SVG **FX star badge** for FX items; clicking the L60 node opens `BundlePanel` — a preview OVER the track that cycles the Iron General Bundle's 7 items with ‹ › arrows + name/type), `ShopPanel.js` (Weapons/Cosmetics/Bundles "Coming Soon" scaffold), `AchievementsPanel.js` (cards → detail view with **reward cards** + hover tooltips), `AchievementToast.js` (queued top-center completion notification that slides down; reward cards; Exo 2 title / Ubuntu body), `weaponPreview.js` (`weaponPreviewSvg()` flat tank+turret(+wrap) SVG), `Tooltip.js` (shared flat animated tooltip — no browser title). ## Conventions

- All world-space objects are added to `engine.world` (via `addToWorld`/`addEntity`) so they pan and zoom with the camera. Screen-space UI (HUD) attaches directly to `app.stage`.
- Outlines are never hand-picked: use the helpers in `shapes.js`, which derive a darker shade of the fill via `darken()`.
- The frame loop calls `entity.update(dt)` then `entity.syncView()`; entities mutate state in `update` and only touch their Pixi view in `syncView`.
- An entity's `view` is positioned (not rotated) at its world spot; anything that rotates (e.g. a tank's barrel) goes in a child sub-container so upright children (health bars) aren't rotated.
- Removal is deferred: set `entity.dead = true` (or call `engine.removeEntity`); the Engine destroys the view during cleanup. Game-wide logic that spawns/removes entities belongs in a **system**, not an entity.

## Visual Style

- Simple geometric shapes (circles, rectangles, polygons)
- Bold outlines: same color as fill but darker shade, thick stroke
- Heavy use of particles and effects

## Architecture Principles

- Keep rendering, input, and camera systems modular and decoupled
- Performance target: 30+ players and bots simultaneously
- No overengineering — build what's needed now
- Do NOT implement full gameplay systems until engine foundation is solid
